## 1. 当前可证实的重复工作

**历史查询是最高优先级。事实**：E:140 在构造每个主组行时调用一次 `previousMainSet`。
R:190 在行 `body` 内调用 `smartProgressionAdvice()`；R:645 的循环逐个历史主组调用同一个 lookup，直到第一次 nil。
H:45 每次建立 descriptor，H:53 限制为最多 50 次训练，H:58 同步 `modelContext.fetch`，H:69 对找到的动作组重新排序 / 过滤。
**50 是单次查询的记录上限，不是整个页面的 fetch 次数上限**。

若一次构建实际求值 M 个当前主组、对应历史含 H 个主组，两条路径合计约为 `M × (H + 2)` 次 helper / fetch 调用，
例如 M=5、H=4 为 30 次；这是静态路径计数示例，不是运行测量。List 的实际求值 / 预取范围、SwiftData 缓存与 SQL / 磁盘访问次数需另测。
建议内容对该动作相同，但当前每行重新收集完整历史；即使已完成行，也没有在 R:190 前跳过。

**聚合重复。事实**：A:615 / A:619 分别遍历组数与完成数，A:896 计算容量；A:556 的大字统计卡多次读取同一 getter。
A:600 先读取 `volumeSeries.count`，A:601 又读取 `volumeSeries`，因此满足条件时会重复 A:628 的排序 / map。
紧凑统计带 A:398 也同时读容量与组数；这类 getter 不是缓存。
**已有优化**：E:53 先排序，E:75 单遍生成行上下文，已替代注释中的 O(n² log n) 编号路径，不能把旧算法写成当前问题。

**键盘宿主更新。事实**：F:49 在每个 UITextField 创建时安装一次自定义键盘；双侧普通行有重量 / 次数两个字段，单侧另有右重量（R:224、R:427、R:482）。
每个已挂载字段各持一个键盘 / hosting controller，不是全页共用一个。F:76 每次 `updateUIView` 都推送上下文；K:457 不比较上下文是否变化，就重新赋值 `host.rootView`（K:473）。
**不是每次按键重新 new UIView**，F:160 已有安装去重。**待测**：实际宿主数量、无关状态更新的 rootView 赋值次数、内存与首开键盘耗时。

## 2. Observation 与输入热路径

- **事实**：重量 / 次数是行局部 `@State`（R:109）；每次文本变化过滤并同步 SwiftData 模型（R:445、R:500、R:891）。
  行重新求值时会走 R:190 的历史收集，因此“仅局部 text 状态”不代表输入路径没有查询。
- **事实**：E:75 的上下文读取主组 weight；A:619、A:896 读取多组训练数据，心率、键盘状态又由根视图 `@State` 驱动（A:52、A:61）。
  `private var xxx: some View` 不是独立 View 结构的隔离边界。**推测**：一次编辑可能导致节上下文、统计及更多内容重新求值。
  SwiftUI 会跟踪已读属性并做子树优化，不能仅据源码断言“每键全页重绘”或具体刷新次数；须用 SwiftUI Instruments 确认。
- **已有优化**：A:420 / A:634 的 1Hz TimelineView 只包计时文本；A:768 的休息计时也局部渲染，T:140 使用睡眠等待 deadline。
  没有证据支持“每秒必定查询全部历史”或“休息每秒同步保存”；重设计不能将整页包进 TimelineView。
- **事实 / 待测**：预设 R:881 与建议填充 R:775 直接同步模型，同时改变的文本还有 onChange 同步路径。
  存在重复调用 setter 的路径，但相同赋值是否被框架合并、实际 observation 通知多少次未测；不能据此声称重复磁盘写。

## 4. 输入 / 完成与持久化边界

**事实**：输入和单组完成回调中没有直接 `modelContext.save()`。R:526 切完成状态、触觉 / 建议接受、回调；
A:832 启动休息，T:39 同步设置日期 / phase 后把通知与 Live Activity 放入异步任务。
所以不能声称“每键 / 每完成一组同步写盘”。SwiftData 自动保存、relationship faulting、telemetry 同步部分是否产生额外阻塞属于**待测**。

**事实**：A:360 在后台切换时同步 save；A:1248 结束训练先同步 save（A:1258），等待 session 结束后可能再次 save（A:1277）再 dismiss；
A:1301 放弃训练也同步 save。后三处用 `try?`，错误没有在此路径呈现给用户。
**推测**：大训练或慢存储可能延长点击结束到返回的时间；尚无 save duration / 错误复现。
不能直接将主 actor 的 ModelContext 塞到 detached task；仅包 `Task {}` 也不证明转去后台线程。
新设计应让“完成此组”“完成输入”“结束训练”命名和区域各自明确，结束的保存中 / 失败行为属于生产实现工作。

**More / 辅助键功能边界（事实）**：K:38 现有左列只有递增、递减、单侧、复制；K:183 递增 / 递减仅工作组启用；
K:225 是次数预设轮换，K:251 的 Done 只收键盘，并不完成组。R:293 的 More 已含删除、组类型、RPE；
动作 More 在 E:211，含 AI 替代、手动替换、删除动作。新加“下一字段 / 完成并下一组”等必须标明提案并指定作用对象，
保持当前输入 / 选择范围、不重复提交；不因扩展面板打开就查询历史或改模型。
